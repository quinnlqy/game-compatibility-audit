# 连续拒审：版本对照、原始资源与模拟盲区

适用于“小工具功能缺陷／可能按钮无法点击”等通用反馈、普通浏览器正常而宿主异常的排查。它是检查策略和历史案例，不是平台审核规则，也不要求其他游戏使用小红书或复制本案例的玩法、包体预算、路径和超时常数。

## 先建立可比较的事实

- 保存审核原文、平台版本、截图时间和用户实际可操作的步骤。原文未指出按钮时，不能把本地找到的第一个缺陷直接命名为审核根因。
- 保留最后通过版、首次拒审版、当前包，比较实际文件清单、逐文件哈希和生产构建源码。主程序压在一个bundle里时，“只变3个文件”不等于只有3处逻辑变化。
- 上传哈希未知时，生成时间和提交顺序只能确定候选关系。不要为了补齐信息反复问已有截图能回答的问题；先完成不依赖答案的检查。
- 通过版仍可能有旧Bug。新旧差异用于排优先级，不构成排除旧代码的证据；空档/已有进度、冷启动/停留后首次打开、实际输入、接口失败/不返回仍需按风险选样。
- 用户能在手机进房间、操作商店，是这些步骤可用的反馈；不能外推成PC模拟器、分享、保存和所有异常路径完整通过。

## 普通浏览器通过，仍需检查什么

### 原始路径与运行时修复是两个阶段

开发系统可能不区分文件名大小写。`exists()`、`is_file()`、`Path.resolve()`成功不足以证明引用与最终包成员拼写相同。

从ZIP成员或目录枚举建立保留大小写的清单，按相对基准词法解析引用后精确比较；查询、片段和URL编码与文件名分开。不要简单把引用和清单全部转小写再声称通过，也不要不确认项目映射规则就重命名全部资产。

运行时图片重映射、预加载、模拟SDK及宽松测试服务器可能在测试观察前修好错误；宿主可能更早解析原始HTML，此时游戏JS的修复还未执行。检查从最终包原始字节开始，并保留缺文件真正返回404的环境。静态工具见[执行手册](execution.md)。

### 输入名称不等于实际转换链

普通浏览器鼠标检查、厂商公开代码本地镜像、实际平台PC模拟器、手机触摸分别记录。若宿主把鼠标转换为触摸和合成click，可记录pointerType、detail、isTrusted与目标，再验证实际操作结果。

合成事件的isTrusted=false或detail=0不是直接拒绝它的依据，也不能仅据这些字段认定是键盘或不合法输入。检验打开/关闭之外的主动作，例如拖动确认、购买扣款、刷新保存；不强行给没有消费的游戏添加购买测试。

### 排查测试工具自身的假象

检查实际用到的SDK版本、账号/关注状态、宿主API集合、存储后端、预热及故障注入顺序。模拟“最新客户端且全部能力成功”不能覆盖旧SDK或真实授权失败；原生存储与浏览器缓存共用同一假后端会掩盖两者的差异。

进程退出码0不等于报告通过：同时看error/passed、失败资源和业务断言。异步提交未完成时立即解析空存档产生的异常属于探针缺陷，应先修正等待条件并重跑，不拿它修改游戏。不要清空玩家数据或绕过存档保护以制造“能进入”。

## 案例：方寸喵居小红书MiniTool，2026-11-04至11-05

### 实际反馈和版本边界

用户连续收到“小工具功能缺陷，可能是页面按钮无法点击，重点排查页面功能完整性”，没有具体按钮或审核端失败日志。用户确认最新分享退出修复包在小红书能进入房间并操作商店，且加入分享后也曾通过。

后续截图确认：平台1.0.7于11月4日10:32生效，1.0.8于13:11开始未通过，之后至1.0.12均未通过。本地10:23拍立得包、12:44高清分享包分别构成通过/首次拒审候选，缺少平台上传哈希，不把时间关系当作精确字节绑定。

两个本地候选均198文件，195文件相同。新增逻辑集中在主bundle：每日分享奖励及收据保存、高清捕获、领奖反馈/入口、话题及照片弹窗安全区。后续应据此提高检查优先级，但不能据首次拒审时间认定奖励违规、擅自删除奖励或排除旧Bug。

### 检查过程与已确认机制

| 检查阶段 | 观察／处理 | 能证明的范围 |
| --- | --- | --- |
| 实际ZIP、严格离线子路径、模拟SDK | 两窗口鼠标、面板、购买、拍照、分享、保存与刷新可用；另构造分享接口不返回、云能力缺失等条件 | 本地条件下的功能和异常路径；构造缺陷不自动等于审核端触发 |
| 异常路径修复 | 分享等待时原先锁住全部照片操作，改为发布请求去重与编辑锁分离；云能力不支持时隐藏无效区 | 已进入具体后续包，但用户仍报告拒审，不能宣布这些修复解决审核 |
| 未修改的厂商公开runtime/service worker本地镜像 | 原始HTML引用`diary_photo_placeholder_Frame.webp`，ZIP只有`diary_photo_placeholder_frame.webp`，预处理产生404 | 确认大小写错误及触发阶段；普通浏览器的运行时映射曾掩盖它 |
| 校验器前后对照 | 原先Windows文件存在检查误过；改为精确清单后旧包失败，修正包通过 | 校验盲区和最小资源修复得到复现，不只是改名后看截图 |
| 厂商鼠标转触摸 | 捕获合成touch/pointer/click，8次面板开关、购买拖动/确认、扣款保存、高清拍立得及重载保留通过 | 指定公开版本本地镜像输入链可用；不是实际创服PC或手机验收 |
| 最终ZIP补测 | 未关注新玩家390×844和1280×800纯鼠标完整流程、5组分享退出/迟到/领奖重试通过；逐文件校验与产物SHA绑定 | 实际包在列出的本地场景通过；SDK发布确认是模拟，未真实发笔记 |

原始大小写错误也存在于较早候选，因此不能仅凭“旧版过审”排除它，也不能说它是首次拒审新增的改动。镜像仍有厂商SDK blob-fetch CSP控制台信息和GPU警告，测试未屏蔽这些信息；未把所有控制台信息都归为致命错误或审核原因。

## 后续审计应改变的决策

1. 较早查看平台版本截图和包哈希，减少无依据的连续补丁/重包；业务功能是否删减应遵循用户授权和明确证据。
2. 资源检查同时覆盖最终包原始引用和运行时结果；静态校验应有一个旧错引用失败、新修引用通过的反例。
3. 检查模拟SDK、预热和宿主预处理差异；有可用公开运行代码时可本地对照，清楚标识版本和不具备的真实宿主能力。没有该工具时不强制搭建整套镜像。
4. 通过版保留为对照，而不是“无Bug”的证明。按玩家影响和复现证据查新增改动与原有异常路径。
5. 新交付包继续绑定SHA和实际解压字节；本地通过、用户过审反馈、实际平台操作和真实设备结果分别更新，不互相替代。
