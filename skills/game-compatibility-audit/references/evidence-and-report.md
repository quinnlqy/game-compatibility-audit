# 状态、证据与交付约定

## 两个维度分别记录

**处理状态**可用：未修复／已有源码修复／已进入指定交付包／已有实机恢复反馈但根因未定／不适用／未知。

**验证记录**每条同时包含环境和结果：

| 环境 | 可以说明什么 | 不能推出什么 |
| --- | --- | --- |
| 静态／编译检查 | 指定资源存在、语法目标与选择器规则满足 | 按钮可用、实际旧内核运行正常 |
| 桌面浏览器运行／触摸或故障模拟 | 指定运行版本下的动作和构造条件结果 | Android／iOS／鸿蒙真机通过 |
| 平台公开运行代码本地镜像 | 指定公开版本在本地条件下的机制 | 实际创服PC模拟器或线上行为相同 |
| 实际平台PC模拟器 | 该平台模拟器、包与鼠标条件下的结果 | 手机触摸、移动GPU和原生弹窗正常 |
| 真实设备＋实际宿主 | 指定型号、系统、客户端、包及步骤结果 | 所有型号通过、全部根因已查明 |
| 用户审核通过反馈 | 用户确认本次提交获准通过 | 不能代替未采集的PC/Android/iOS操作证据，也不单独证明某补丁是唯一原因 |
| 用户恢复反馈 | 用户报告该次现象恢复 | 缺包指纹时不能绑定候选哈希，重开恢复不证明首次进入已稳定 |

环境不是必经的线性等级；PC模拟器与手机、不同设备各有独立结果。结果可为通过／失败／未执行／证据不足／不适用。

## 单条问题记录

按任务规模用表格或简短段落，不强制生成JSON和复杂目录。至少能回答：

- 问题、优先级与玩家影响；已确认失败还是待复测风险。
- 目标／包指纹、设备和宿主、可用区域与输入方式。
- 复现步骤、预期与实际；原玩家观察和本地注入分别标记。
- 当前代码／包处理状态、已验证环境和结果、证据路径。
- 缺哪一步、在哪个环境上验证才能关闭。

例如：“已进入X包，桌面缺接口模拟通过；原Android设备未复测。需同包冷启动、打开商店、购买、刷新确认。”不要缩写为“已解决”。

## 报告建议

1. 开头回答最高影响的问题、当前工作结果和主要证据缺口。
2. 按优先级列清单，区分未修复、已修待验、真实反馈恢复与设计限制；注明本轮新跑和继承的历史结果。
3. 给出可直接执行的下一轮复测步骤，注明目标环境和成功标准。无法访问的设备不伪装成已执行；能做的检查继续完成。
4. 若有修复，写影响目标和是否重打实际包；上传／提审／上线单独说明。

测试场景数不是故障数、设备数或玩家数。没有投诉总数、活跃设备和样本来源时，不做品牌故障率排行。型号只保留实际披露代码；不能根据CSS尺寸猜手机型号或自行映射商品名。

## 状态判定中的常见陷阱

- 以前过审只说明当次检查没有拦截，不证明旧版没有Bug；新增改动对照与潜在旧故障检查应并行保留，按可复现影响决定优先级。
- 同一次只修一处、同包随后过审能缩小关联范围，仍应分别记录已证实的代码机制和用户审核反馈；缺少审核端失败步骤/日志时不宣称因果闭环。
- 测试进程退出码0不保证报告通过；解析报告中的error/passed及实际断言。等待异步提交后再核对状态，测试过早读取空存档不算游戏故障。
- 同一句图片失败可能先后由不同机制触发；一次路径修正不证明资源生命周期也正常。
- 旧文档“未打包”可能已经被后续实际ZIP覆盖；确认修复进入哪个具体包，不只按文档新旧推断。
- 玩家“重开好了”保留为恢复事实；没有日志不归因为缓存、SDK或系统品牌。
- 原始专项测试与当前完整游戏使用不同材质／加载器时，分别报告；历史失败不能直接称为当前未修复。
- 存储权限持续拒绝时的安全拦截与代码故障不同；不承诺网页补丁能恢复设备权限，也不通过跳过保护伪造正常。
- 平台规则、项目预算、用户后台实测限制分开；没有核对现行来源时明确采用历史资料。

## 可选机器核对

移动H5实际包需要逐项核对时，可采用[执行文档](execution.md)中的JSON计划和脚本；普通专项沿用本报告格式即可。机器核对只验证范围完整、证据结构与哈希匹配，不证明操作真的执行，也不替代实际PC模拟器／真机。

脚本输出的`local_complete`、`device_complete`只限记录中的目标和检查项。`scope.mode=targeted`的完成不能写成全量49项通过；缺少设备时可以交付已完成的检查与明确缺口，不能伪造通过来消除待验。
